# Memex: Website ↔ Desktop Realignment

## Context

Tonight's debugging session (model-selection wiring for Collective runs) surfaced the
actual root cause behind repeated confusion: **two backend trees are being maintained
as if they were one product.** `Memex_Core` (Lovelace) is demonstrably ahead —
`role_model_resolver.py`'s single-model snapshot binding doesn't exist at all in
`Agent_Swarm` (Turing) — yet the public "Memex Anywhere" profile silently routes to
the older tree, so a real fix landed in one place and not the other.

Decision made: stop trying to keep the public website (`Memex_Core/ui`, deployed on
Turing behind `memex.shivelymedia.com`) at feature parity with the Desktop app. The
website becomes a **media/download/info site plus an admin/fleet-ops backend**; the
Desktop app becomes **the one place real development, routing, and swarm work
happens** — each install pointing at whatever inference engine(s) its own user
brings (their own Ollama, their own llama.cpp, their own rig), not a shared hosted
backend. Desktop also gains a **guided local-infra setup** so a brand-new user with
nothing installed can get running.

This plan covers three phases: (A) prune the website down to its new scope, (B)
confirm the desktop app needs no new dev/runtime features (it already has them —
this is a subtraction project on the website side, not new desktop work), and (C)
build the guided Ollama/llama.cpp install flow.

## Phase A — Website (`Memex_Core/ui`) split

`ui/` is a Next.js app (`ui/src/app/...`) with two coupled things: page routes and
server-side API proxy routes (`ui/src/app/api/**`) that the *outside world* uses to
reach the backend — including `api/backend/[...path]`, the exact catch-all proxy
`https://memex.shivelymedia.com/api/backend` resolves through, which is what the
Desktop app's **"Memex Anywhere" profile depends on**. Pruning has to distinguish
"duplicated product surface" (delete) from "infrastructure the Desktop app still
calls" (keep).

**Keep (admin/fleet-ops + infra):**
- Pages: `ops/`, `monitor/`, `monitoring/`, `governance/`, `mission-control/`, `docs/`
- API routes: `api/devops/**` (git, ssh, log streaming), `api/grafana/[...path]`,
  `api/langfuse/[...path]`, `api/maintenance/[...path]`, `api/services/health`,
  `api/auth/**` (Authentik session)
- **`api/backend/[...path]`** — do not remove; this is the tunnel proxy the Desktop
  app's remote profile uses. Removing it breaks "Memex Anywhere" entirely, which is
  a separate decision (see Open Question below), not a side effect of this cleanup.

**Remove (product surface, now desktop-only):**
- Pages: `swarm/`, `dev/`, `tools/`, `routines/`, `research/`, `art-studio/`,
  `training/`, `control/`, `palace/`, and their dedicated component trees under
  `ui/src/components/{swarm,dev,tools,routines,training,art-studio,palace,...}`
- Corresponding nav entries in `ui/src/components/layout` (or wherever the site nav
  is defined — confirm exact file during implementation)

**Add (new scope):**
- A landing/download page (link to the Desktop app installers once Phase C's
  multi-platform builds exist)
- Media/info content pages per your existing `docs/` pattern

## Phase B — Desktop app: no new runtime work needed

The Desktop app (`memex-desktop`) already has the dev/runtime surface this plan
consolidates onto: chat + Collective (`InputBar.tsx`, `sse-stream.ts`), Scheduled
Tasks, model picker (`ModelPickerPopover.tsx`), and multi-profile routing
(`electron/config-store.ts`). This phase is a **verification pass, not new
construction**: confirm nothing the website's removed pages did (e.g. `art-studio/`,
`training/`) has a gap on the desktop side before those website pages go away. Flag
any real gap found as its own follow-up rather than blocking the website prune on it.

## Phase C — Guided local-infra setup (Ollama / llama.cpp)

Extends existing, partially-built scaffolding — this is *not* greenfield:

- `src/components/onboarding/SetupWizard.tsx` already does hardware inspection
  (RAM, GPU + VRAM), model recommendations, and an Ollama reachability/pull flow.
- `electron/local-llm.ts` already has `inspectLocalLlm()` and
  `recommendLocalModels()`.
- What's missing: `openOllamaDownload()` today only opens a browser tab — there is
  no actual installer automation, no llama.cpp path at all, and electron-builder's
  `package.json` currently only configures a **Windows/nsis** target (no `mac` or
  `linux` block yet), so cross-platform distribution isn't wired up regardless of
  the installer work.

**C1 — Engine choice UI** (new wizard step, before the existing Ollama step):
Explain the real trade-off surfaced tonight — Ollama is the multi-model swap engine
(loads/evicts on demand, needed for Team Builder-style per-role model variety);
llama.cpp is a single pinned model with disk-persisted KV-cache (`/slots/save|restore`),
worth it for one long-context, latency-critical lane, at the cost of not swapping
models on demand. Let the user pick Ollama, llama.cpp, or both — no silent default.

**C2 — Per-OS installers**, new functions in `electron/local-llm.ts` alongside the
existing `inspectLocalLlm`:
- Ollama: `winget install Ollama.Ollama` (Windows) / `brew install ollama` or the
  official `.dmg` (macOS) / the official `curl -fsSL https://ollama.com/install.sh | sh`
  (Linux)
- llama.cpp: use prebuilt per-OS binary releases from the `ggml-org/llama.cpp`
  GitHub releases — **not** a Docker Desktop requirement, since a "brand new user"
  shouldn't need Docker as a prerequisite (this differs from how your own Lovelace
  rig runs it tonight; document that divergence in the wizard copy)
- Every install action is a real system change (installing software, possibly
  invoking `sudo`/UAC) — each one gets an explicit confirm step in the wizard before
  running, consistent with how this session has treated other system-modifying
  actions; no silent/background installs.

**C3 — electron-builder multi-platform packaging**: add `mac` (dmg) and `linux`
(AppImage/deb) target blocks to `package.json`'s `build` config, alongside the
existing `win`/`nsis` block. Prerequisite for C1/C2 to reach non-Windows users at
all — currently unbuilt for those platforms regardless of installer code.

## Open question — remote access to Lovelace

`api/backend/[...path]` is kept in Phase A specifically because "Memex Anywhere"
depends on it today, tunneling to **Turing's** `Agent_Swarm` backend — the tree that
still lacks the model-selection fix from earlier tonight. This plan does not decide
whether to (a) port that fix to `Agent_Swarm` so remote access stays fully
functional, or (b) leave remote access on `Agent_Swarm` as a known-degraded path and
treat "reach Lovelace from outside the LAN" as a separate, later problem. Flagging
so it isn't silently decided by omission — worth a explicit call before Phase A ships.

# Desktop-side realignment (added 2026-09-24, after the open question was answered)

Owner decisions recorded this session, verbatim intent:

1. **"There will be no more Memex Anywhere."** The hosted profile dies. The open question above is
   closed by deletion — `api/backend/[...path]` no longer needs keeping *for the desktop*; whether the
   site's own admin pages still call it is now a Phase A question only, and the Phase A verification
   step that curls that endpoint is no longer a desktop acceptance check.
2. **Desktop owns model routing; `config.json` is the source of truth** (the qwen-code / codex shape:
   a hand-editable file that assigns models to features). The runtime honours what the client declares
   instead of resolving roles against a shared host.
3. **Guided setup is keyed on run style.** The user picks how their box runs — one pinned model on one
   GPU, or multi-model across one-or-more GPUs — and the wizard installs and configures the engine
   (Ollama or llama.cpp) that matches, so the Memex features actually work in that mode.
4. **The desktop controls Team Builder's per-role map** (owner, 2026-09-24: "The desktop should be
   controlling the Team Builder's map, since this is a local harness"). Consequence, and it is the shape
   D1c takes: the runtime stops deciding roles from its own environment and accepts a client-supplied map,
   which means a new request field, a third snapshot `source`, and honouring it on restore instead of
   coercing it back to `team_builder` (`role_model_resolver.py:175` collapses anything unknown).
   **Name the keys against the runtime's actual roles, not the desktop's current slots.**
   `_SWARM_ROLES` is `coordinator, architect, coder, devops, researcher, analyst, verifier` — seven. D2's
   slots are `default, code, collective.coordinator, collective.critic, embedding` — five, and two of them
   (`critic`, `embedding`) are not swarm roles at all while four roles have no slot. A map keyed by the
   slot names would be accepted by a permissive server and bound to nothing, which is the silent no-op this
   project keeps recording. Decide explicitly, in D1c: which slots project onto which roles, and what the
   app does with a role it has no slot for.

5. **Setup is scenario-driven; "where the orchestrator lives" is an output, not a choice.** Owner,
   2026-09-24: multi-model on one GPU → the orchestrator runs on this machine beside that card; multi-model
   on multiple GPUs → same, but with a per-GPU assignment layout; LAN / homelab → the user organises the
   orchestrator placement **and the agent roster** around the topology the wizard identified. In their
   words: *"It's not so important of 'where', but that the proper assignments/setup is performed with
   whatever that scenario is."* Consequences:

   - The wizard's product is a **topology + assignment set**, not a model dropdown. Shape: scenario →
     engines and lanes → which GPU each lane may use → which model each role gets → confirm → write. This
     re-scopes D3a-2's "slot editor" into **role assignment against the runtime's seven roles**, which is
     what decision 4 already implies.
   - `config.json` needs a lane→GPU field it does not have. `engines.<id>` today carries only
     `kind`/`baseUrl`/`label`/`pinnedModel`; nothing expresses "this llama.cpp lane lives on card 1", which
     the multi-GPU scenario requires and `gpu_queue` already enforces server-side.
   - **"Only while the app is open" is a requirement on a future scenario, not a present-tense fact — my
     earlier wording was wrong and is corrected here.** The owner chose that routine behaviour for the local
     scenarios, and it is a real decision about what the *managed* local runtime will be. But today the
     scheduler is not the desktop's: it lives in `agents/trigger_scheduler.py` inside the runtime process,
     and `ScheduledTasks.tsx`'s own header records that `task_config` triggers **"survive a backend
     restart"** — they are re-registered from the store when the runtime starts. So on the current Localhost
     profile, which is a Docker container that outlives the app, closing Memex does **not** stop routines
     from firing. The accurate rule for both placements today is: *a routine fires while the runtime process
     is up, and survives that runtime restarting; the desktop's own lifetime is not in the chain.* It only
     becomes "while Memex is running" once the app supervises the runtime process (D3's managed local
     install), at which point the sentence genuinely depends on placement — supervised local → app lifetime;
     homelab → the host's service lifetime.
   - **What the Routines screen should therefore say now:** which runtime it is talking to, by host, and what
     that implies — not a promise about the app's lifetime that the code cannot keep. A copy line that is
     true today beats one that anticipates D3.
   - **D1c survives every branch of this decision.** Whether the orchestrator is app-supervised locally or
     organised by the user on the homelab, the desktop still has to *send* the role map and the runtime still
     has to *honour* it. What changes is the deployment hazard: if the app ships and supervises the runtime,
     the two halves of the contract ship together and can never be half-applied — which is precisely the
     risk that made me insist on runtime-first for a separately-deployed server.

- **D3's "managed local runtime" is the absorption mechanism, not a packaging nicety.** The app installing,

  one artifact. That promotes it from "largest unbuilt item" to the structural goal the other items serve —
  and it is why `orchestrator.placement` is still deliberately unstored: the field becomes meaningful when
  there is an install to point at, not before.

Naming rule for live documents: say **the orchestrator the app drives** (or name the deployment —
`agent_runtime` on `:8008`) rather than treating `Memex_Core` as a peer authority. Dated records —
`MEMEX_CODE_QOL_PLAN.md`, the earlier items of `MEMEX_CORE_HANDOFF.md`, Phase A's prose in this file — keep
their wording, because they describe the tree as it was understood when they were written.

6. **The orchestrator is a role, not a service** (owner, 2026-09-25). *"If there is a multi-gpu / multi-model
   setup then the orchestrator will be the 'big model' and the agents will be whatever the smaller 'agent
   model' is that fits and is capable or specifically setup by the user. If the setup is a single model

   orchestrator."* And: *"There is no 'online mode', everything is about the harness and the llama.cpp /

   - The question this plan kept asking — *where does the orchestrator run* — was the wrong question. In the

   - "No online mode" retires the framing behind Memex Anywhere completely: there is no attachable hosted

   - `SNAPSHOT_SOURCE_SINGLE` is this decision, already: one model bound to all seven roles. The missing
     half is not infrastructure, it is a **persona/framework distinction** — the same weights answering as

   - It also makes D1c the load-bearing item rather than S1's migration debate: bind the roles, and the

## S1 — What "supervise the orchestrator" actually costs (design, 2026-09-25)

> **Scope note after decision 6: this section prices the wrong target, and is kept as a census rather than a
> plan.** It answers "how would the app absorb the server that exists today", and the owner's answer was
> that there is no server to absorb — the orchestrator is a role filled by a model. Read what follows as
> documentation of the legacy dependency graph, which is useful: it is what has to be *retired*, and the
> house-specific compose defaults listed here are real defects on that path. It is not the shape of the
> harness.

**My earlier sizing was wrong and is retracted.** I described the managed local runtime as "days to weeks
of packaging" on the assumption that the thing to supervise is one process. It isn't. Evidence, read this
session:

- `Memex_Core/control_plane/docker-compose.yml` defines `docker-socket-proxy`, `spire-server` (SPIFFE),
  `postgres` (**pgvector/pg15**), `mempalace`, `clickhouse`, `langfuse-web`, `langfuse-worker`, `redis`,
  `minio` plus five named volumes.
- `execution_plane/docker-compose.yml` is ~1,200 lines and adds `spire-agent`, `ollama`, `openhands`,
  `dev-sandbox`, `android-builder`, `agent-runtime`, an Authentik stack with its own Postgres, and two
  gateway services. Its defaults hard-code this house: `MEMPALACE_API_URL` → `http://192.168.2.102:8200`,
  `NEXT_PUBLIC_GATEWAY_URL` → `http://192.168.2.101:8008`, `HOME_ASSISTANT_URL` → `192.168.2.100:8123`.
- Postgres is not an optional service. `import psycopg2` sits at **module scope** in at least ten files
  under `agents/` — `conversation_store.py`, `dev_sessions/store.py`, `dev_projects/store.py` +
  `routes.py`, `dev_harness/approval_service.py` and `dev_harness/checkpoints.py`, `dev_files/routes.py`,
  `coordination/workspace_lifecycle.py`, `github_publish_audit_store.py`. `redis` likewise (`inject_task.py`,
  and `utils/gpu_queue.py` per the 2026-09-23 capability check). There is no storage abstraction to switch on.
- The serving container still has **no GPU access** (`pynvml` present, `nvmlInit` → `LibraryNotFound`), so
  capacity remains a declared fact, not a measurement — unchanged since 2026-09-23.

So absorption is a **port with a substitution table**, and the parts are separable in cost, which is the
useful thing to say about it:

| Concern | Today | Local substitution options |
| --- | --- | --- |
| Durable store (sessions, approvals, checkpoints, workspace lifecycle, audit) | Postgres + psycopg2, pervasive | (A) ship and supervise an embedded Postgres; (B) put a SQLite-backed layer under the stores; (D) don't absorb this half |
| Coordination / locks / GPU queue | Redis | (A) ship Redis; (B) in-process locks on a single box, which is legitimate *because* it is now single-user |
| Observability: ClickHouse, Langfuse, MinIO | full stack | off, or "point at a server" — no harness feature depends on them |
| Identity: SPIRE, Authentik | machine identity + SSO | nothing. Decision 1 deleted the hosted path and the app already carries its own uid (`X-authentik-uid`, `identity.enc`) |
| Sandbox execution: `dev-sandbox`, `openhands`, docker-socket-proxy | containers, Docker required | the app already has its own workspace policy, permission store and PTY layer — the overlap is the honest candidate |
| Inference | Ollama / llama.cpp | already the app's own decision (D1/D3/D4) |

**Options, and the one I'd take.**

- **(A) Embed the services.** Shipped Postgres + Redis, app-managed data dir, port allocation, upgrades,
  WAL, the works. Least new code, largest artifact, and every failure mode of running a database server on a
  customer laptop becomes ours.
- **(B) Abstract the stores to SQLite.** Smallest artifact and the right long-term shape for a single-user
  desktop, but it touches ~10 store modules and needs an audit of what Postgres features they actually use —
  JSONB, pgvector, advisory locks, `RETURNING`, upsert shapes. Not free, and not yet costed.
- **(C) Install a bundle the app doesn't absorb** (its own compose or a runtime installer). Honest and fast,
  but reintroduces the Docker prerequisite the plan rejects for llama.cpp, and keeps two artifacts that can
  version-skew.
- **(D) Split the harness — absorb the stateless half.** Chat, code and single-turn work run in the app
  against the user's own engine; durable multi-agent orchestration stays a service you attach to, local or
  remote, and the feature set states which features need it. This matches "each install points at its own
  inference engine" and the capability matrix in D4, and it is the only option that doesn't require solving
  the store problem before the app is usable anywhere but this machine.

**Recommendation: D, with C offered as the homelab path, and B revisited only after it is costed.** Not
because D is cheap — it means admitting some features are remote — but because A and B both require deciding
the durability question first, and pretending otherwise is how a plan gets a "packaging" line item that turns
out to be a migration.

**Costing step before anything is ruled out (research, no code):** enumerate what those ten `psycopg2`
modules actually use — tables, JSONB, `pgvector`, advisory locks, `INSERT … ON CONFLICT`, `RETURNING` — and
count what a SQLite backend would have to reproduce. Until that list exists, B is an opinion.

**Decision points for the owner:** (1) is a fresh install allowed to have no durable orchestration — i.e.
is D acceptable, or is "Collective works offline on my laptop" a requirement? (2) If D: which features are
allowed to say "needs a runtime", and does that list live in D4's matrix where the rest of the honesty
rules already live?

## D4 — Model/feature compatibility matrix

"Staying as model compatible as we can with the feature set" is only enforceable as a table. Each Memex
feature names the capability it needs; the app checks the selected model against it and says so up
front. This is the direct answer to the failure class this project has been bitten by repeatedly — the
Gauntlet quality bar parsed and discarded, `research_mode` never reaching the coordinator, a completion
record implying a critic loop that never ran. Silent degradation is the bug; the matrix is the guard.

| Feature | Capability the model must have | If it doesn't |
| --- | --- | --- |
| Chat | instruction following, streaming | — baseline, everything supports it |
| Code / DevHarness | reliable tool + function calling (read/write/edit/exec round-trips) | disable the workspace, state why, point at a capable model |
| Collective coordinator | tool calling **and** long context (the perspective matrix plus its transcripts) | warn before the run; short-context models truncate silently |
| Collective critic / Gauntlet verdict | strict structured output — the verdict grammar (`VERDICT: PASS`) is parse-critical | refuse Gauntlet rather than run a critic that can emit unparsable verdicts |
| Research / Perspectives | several concurrent lanes, or one lane re-used serially | run-style dependent; single style collapses to serial |
| Memory (MemPalace) | a reachable **embedding** model — a separate slot from the chat model, `nomic-embed-text` today | memory writes queue instead of failing the turn |
| Image grounding / Design | vision input | hide the attach control for that model, don't 400 at send time |
| CAD / OpenSCAD, Unreal lanes | tool execution + long context | existing feature gates; the matrix should be the single source, not per-feature `if`s |

Acceptance for D4, per row: pick a model that lacks the capability, and the app must state the limitation
before the request rather than produce a transcript that implies capability it did not use. Where the
model registry can answer the question (`/api/show` capabilities on Ollama, `/props` on llama.cpp) the
matrix is derived; where it can't, the capability is a user-editable field in the routing entry — never a
guess baked into `src/`.

## D5 — why `engine` is NOT going on the wire, and what replaces it (2026-09-25)

D1c's second half was written down as "`engine` + role map on the wire". The role map shipped (`50e5ca0` +
`3efe4a5`, accepted from the packaged app). **`engine` should not be built as specified**, and the reason is
that the runtime already decides placement — so the field would state something the enforcement ignores.

Read from `Memex_Core/agents/utils/gpu_queue.py` (1,272 lines) and the live `:8009` response:

1. **Host choice is derived from the model id, not supplied.** `get_best_host_for_model()` (line 200) prefers
   a host with the model already hot in VRAM, then a host where it exists on disk, then
   `get_ollama_host(model_name)`. Every handler resolves its own host at call time — 26 call sites, including
   `church.py:1210`, `handlers/architect.py:53`, `main.py:6743`.
2. **The tie-breaker is a substring allowlist, not measured memory.** `_get_preferred_host()` (line 136)
   sends a model to Turing only if its name matches `_TURING_MODEL_MARKERS`; their own comment warns
   `"qwen3:8b" must not match "qwen3:14b"`. Everything else goes to Lovelace.
3. **The two host variables mean opposite things depending on which machine runs the container.** Their NOTE
   (line ~157): on Turing `OLLAMA_HOST` is Lovelace and `SECONDARY_OLLAMA_HOST` is local; on Lovelace it is
   the reverse. So a URL the app calls "the ollama lane" does not carry the same meaning across installs.
4. **Capacity is declared, not measured — and the container I first probed is the blind one.** `GET
   /api/v1/health/nodes` on **`:8009` (`agent_runtime_dev`)** returned `vram_mb: null, vram_source:
   "unknown"` for both nodes, and I read that as the general state. It is not: the same call on **`:8008`
   (`agent_runtime`)** answers `Lovelace · vram_mb 32622 · vram_source "configured"`, because
   `execution_plane/docker-compose.yml:444` sets `LOVELACE_VRAM_MB=32622` with a comment saying the
   container has no NVML and no `/dev/nvidia*`. So the real gap is narrower than "capacity must be
   declared": **`TURING_VRAM_MB` is set nowhere** (`:8008` reports Turing unknown) and **`agent_runtime_dev`
   carries neither variable**. `LOVELACE_VRAM_MB` appears exactly once in the file. Turing's true size was
   measured over SSH on 2026-09-26: `RTX 3070 Ti, 8192 MiB`; `nvidia-smi` inside `ollama_gpu` sees no
   devices (`Unable to determine the device handle for GPU0/GPU1`, exit 6), so declared capacity is the only
   honest source on this box. The consuming code (`agents/inference/node_health.py` — `VRAM_ENV_BY_NAME`,
   `_resolve_node_vram`, `_host_is_local`) and `tests/test_node_vram_reporting.py` are **uncommitted** in

   `docker exec -e LOVELACE_VRAM_MB=32640 agent_runtime_dev python -c …` → `(32640, 'configured')`, and the

5. **The app already fetches this and throws it away.** `electron/health.ts:48` calls

   run, are discarded. `local-llm.ts:167` likewise uses it only for reachability.

**Decision, replacing the old item:** sending `engine` per request would either be ignored by (1)–(3) or
override the residency preference and cause the reload/evict churn `gpu_queue` exists to prevent, so it is
**not built**. Placement stays an output of the scenario, per decision 5. What gets built instead is **D5:
read the node report the runtime already gives**, in three pieces —

- Parse `/api/v1/health/nodes` into typed per-node records (name, host, healthy, `available_models`,

- Show it where roles are assigned, and use it to make the row's sentence accurate: a node with

  host *does* hold stops being described as doomed.
- `lane→GPU` then means **declared capacity on the runtime host** (`OLLAMA_HOST` / `SECONDARY_OLLAMA_HOST` /
  the markers list, i.e. compose env, which is where enforcement actually lives), surfaced to the app for

possible in every case. It also corrects an overreach already in that sentence: "will fail until that model
exists on the lane" assumed the app's lane is where a model loads, and (1) says it isn't necessarily.
(c) When the runtime is unreachable, the role editor behaves exactly as before, with no runtime clause added.
(d) No new claim is written into `config.json` — the topology is read per session, because it is runtime
state, not user intent.

## D6 — OpenRouter as a connected provider (added 2026-09-28)

**Asked:** "i would like to see if i can add my open router connection to the app."

**What is already true, read rather than assumed.** The harness has a working per-user provider-key
subsystem and the desktop does not touch it:

**Owner ruling for this item:** attach it as a runtime provider *and* build the desktop UI; enumerate
OpenRouter's models **live** from `https://openrouter.ai/api/v1/models` rather than hardcoding a list.

**The constraint that decides the shape.** OpenRouter ids are `vendor/model`, and the NVIDIA catalogue
already ships `mistralai/mistral-nemotron` and `deepseek-ai/deepseek-v4-pro`. `registry.py:6-9` warns in
so many words against prefix matching for exactly this reason, so **membership in the cached catalogue is
the only safe dispatch signal** — which means the live list must be *stored*, not merely proxied, and a cold
cache is a correctness problem rather than a latency one.

**Three slices, in this order.**

1. **Runtime: `openrouter` provider.** Catalogue entry with `key_prefix: "sk-or-"` and
   `validate_url: https://openrouter.ai/api/v1/models` (public, needs no key);
   `providers/openrouter_provider.py` as an OpenAI-compatible client beside `nvidia_provider.py`; a
   `provider_for` index fed by a **cached** live model list; a dispatch branch in `/v1/chat/completions`.
   Cache policy: populated on `connect`, refreshed on demand, and a stale cache may only *add* ids — it
   must never silently drop a model the user can already see.
2. **Desktop: Settings → Model providers.** Catalogue, connected state, connect/disconnect, behind
   no-argument IPC channels that resolve `config.getUrls().agentRuntime` — the `runtime:nodes` pattern, so
   the renderer never supplies a URL and the key never lives on the client.
3. **Deferred, stated rather than hidden:** a provider-backed model **in a role** (`role_models`, Team
   Builder / coordination). Every agent and handler resolves an Ollama host from the model name
   (`get_best_host_for_model`, ~20 call sites across `handlers/`, `dijkstra_agent.py`, `leibniz_agent.py`),
   so a role bound to an OpenRouter id would be looked up on Ollama and fail. Slice 1 makes OpenRouter work
   for a **turn**, not for an **orchestrator role** — which is the case decision 6 actually cares about, and
   it needs its own design instead of being folded in here.

**Acceptance.**
(a) `GET /api/v1/provider-keys/providers` lists `openrouter` with a non-empty model set, and the desktop's

(b) `POST /connect` with a valid key returns `connected`, stores it encrypted, and populates the cache; a

(c) A desktop Chat turn naming an OpenRouter model streams an answer and the harness never attempts an

(d) A `nvidia/…` or `mistralai/mistral-nemotron` turn still routes to NVIDIA — the regression that prefix
    matching would have caused, guarded by a test rather than by care.
(e) Disconnect leaves the catalogue browsable and its models listed, with a connect prompt instead of an
    empty pane.

## D7 — which provider models are *my* options (shape agreed 2026-09-28, built 2026-09-29, native pass owed)

**Owner steer that created this item:** "usually when using OpenRouter with other harness, you typically
identify which models you actually want as options from openrouter." Inherited mode currently exposes all
**460** fetched OpenRouter models — a firehose, not a menu.

**What already exists, so this is not a new layer.** `user_permissions.allowed_models` is `null`
(inherited = the whole operational catalogue) or an explicit list, and it is enforced at three points
already: `/v1/models` output, the picker, and the D6 gate branch. The admin **User permissions** screen
renders it as "Explicit allowlist" with a filter and per-model checkboxes
(`UserPermissionsView.tsx:106-107`).

**The landmine found while checking that, which is a bug and not a design question.**
`permission_catalog` (`main.py:914-919`) builds its list from `model_registry.get_user_selectable_models()`
only — **no provider models**. So the allowlist UI can never show an OpenRouter id, therefore cannot admit
one, and because `allowed_models` denies everything absent once non-null, **the first explicit allowlist set
for any reason turns off every provider model with a 403 that names no reason** — including through the D6
branch, which calls `model_allowed`. Latent today only because this install's policy is `null`, which is
exactly why acceptance (c) passed. Fixing the catalogue is a precondition for everything below, and is
arguably worth landing on its own.

**Agreed shape: a separate per-provider selection, alongside `allowed_models` rather than inside it.**
Rationale for not reusing the global list: seeding it on connect would mutate a global policy as a side
effect of adding one credential, and `null` already means "everything" — "connected but showing nothing"
is unexpressible in it.

- **Storage:** a `selected_models` column on `swarm.provider_api_keys`, colocated with the credential so
  disconnecting clears the selection with the key and the lifecycle cannot drift. Alternative considered
  and rejected: a second table, which buys nothing here and adds a join to every list call.
- **Scope of the new default:** applies to `live_models` providers only. Curated providers
  (anthropic/google/nvidia, 3–8 models each) keep today's all-or-nothing behaviour — the distinction is
  measured, not aesthetic: a handful is a menu, 460 is a firehose. Making existing users opt in
  retroactively would be a silent behaviour change under cover of a new feature.
- **Semantics:** key + empty selection → **zero** rows offered; key + selection → exactly those ids;
  no key → unchanged (nothing offered, connect prompt).

**Acceptance.**
(a) Connecting OpenRouter changes `/v1/models` by **zero** rows. This is the whole point of the item and the
    first thing to assert.
(b) Selecting two models makes exactly those two appear for that user, and a turn on either succeeds.
(c) A turn on a *fetched* OpenRouter id that was not selected is refused with a message naming the
    selection control — not a bare 403 into nowhere.
(d) Disconnect clears both the key and the selection; `/v1/models` returns to its pre-connect shape.
(e) **No regression for curated providers:** anthropic/google/nvidia behave exactly as before, asserted
    rather than assumed, since the new default is deliberately not applied to them.
(f) `permission_catalog` lists provider models for a user with a connected key, so the admin allowlist can
    express them — the landmine, closed.
(g) The desktop picker reads `/v1/models`: a provider model is selectable, writes `routing.default` like any
    other row, and the 6 shadowed ids are marked *answered elsewhere*, not hidden.
(h) A native pass on both screens, which D6's own screen has not had.

**Order:** f → a/b/c/d (harness) → g (desktop, needs a build) → h. **e is written before the change that
could break it**, not after.

**Built 2026-09-28 — the harness half (f, a, b, c, d, e). Not deployed, desktop half not started.**
`swarm.provider_api_keys` gains `selected_models TEXT[]` via an idempotent `ALTER … ADD COLUMN IF NOT
EXISTS`, colocated with the key so disconnect clears both; `ProviderKey.get_selection()` and
`registry.provider_selection()` keep **None (no key)** distinct from **[] (connected, nothing chosen)**;
`set_selection` + `normalize_selection` refuse an unknown provider and de-duplicate, sort, trim and
**drop non-strings**; `/v1/models` filters a live provider's catalogue to the selection while curated
providers never reach that branch; `_apply_model_policy` denies an unselected gateway model with the
control that would add it; `permission_catalog` now lists provider models for the caller's connected keys
(the landmine, closed); `PUT /api/v1/provider-keys/{provider}/selection` is the new write, and
`/list` reports `selected_models` so checkboxes render as chosen rather than as an empty offer.
`tests/test_provider_selection.py`: 15 tests; 92 pass across the provider/permission selection with the
same 5 pre-existing collection errors.

**One bug the new test caught in code written minutes earlier:** `normalize_selection` used
`str(m).strip()`, and `str(None)` is `"None"` — truthy — so a null in the request body would have been
stored as a model id called `None` and offered back to the user as a choice. Fixed to accept strings only.

**Known limit, stated not hidden:** `permission_catalog` takes no owner parameter, so it lists providers for
the **requesting admin's** own keys. Per-owner catalogues are the honest generalisation and are not built.

**Built 2026-09-29 — the desktop half (g), with one deviation from the wording.** Selection checkboxes on
Settings → *Model providers* for a connected **live** provider, written whole-list on save through
`providers:selection` (a fourth no-argument channel), reading `/list`'s `selected_models`; curated providers

list additively, skipping the rows the runtime tags `owned_by: MarsRL` so its operational catalogue is not

answers it.

**The deviation: a gateway row does not write `routing.default`, as (g) said it should.** The criterion was
written before the table's grammar was read. `validateRouting` refuses a `routing.<slot>.engine` that is not
in `engines`, and `KNOWN_KINDS` is `ollama` and `llama.cpp` — a gateway is not a lane, so writing
`meta-llama/llama-3.1-70b-instruct` against `ollama` would record that a local engine serves a model it
cannot serve, and under `runStyle: "single"` the engine's `pinnedModel` would name it too. The honest
consequence is that the profile's `defaultModel` — which the table outranks on load, by design — would revert
every gateway pick on the next start, so the pick now carries provenance:
`defaultModelSource: "engine" | "gateway"`, absent meaning `engine` for every profile written before this.
`applyProfile` honours a gateway record above `routing.default` and the trigger names both facts (who serves
this model, what the table still resolves for the rest). What (g) meant by "like any other row" — the pick is
selectable and it persists — holds; the mechanism is the profile, not the table.

**One thing a test proved about the widget rather than the code:** a disabled checkbox still fires its React
`onChange` under `fireEvent.click`, so the shadowed-id guard lives in `toggleModel` as well as on the
control. The invariant is that a selection never contains an id the runtime routes elsewhere, and that cannot
be delegated to whether a click lands.

**A second thing, proved by the owner looking at a screen rather than by any test of mine.** The first
packaged build of this half (`0.1.117`) could not show the selection editor at all: the whole control is
gated on `provider.live`, and `parseProviderCatalog` derived `live` from `info.live_models` — which is a key
of the harness's internal `PROVIDERS` dict and is **not** in the `/providers` response. Read live on
2026-09-29: `openrouter -> label, models, catalog`, the curated three `-> label, models`. The reader's own
test fixture had `live_models: true` written into it from the assumption rather than from the capture, so 486
tests passed against a payload that does not exist and the gateway rendered as curated. `live` now comes from
the `catalog` block, which the runtime attaches to exactly the fetched entries. The rule this leaves behind:
**a fixture standing in for a runtime response is written from a live request, and states what the payload
does not contain.**

**Interaction changed 2026-09-29, on the owner's steer, before any build was installed.** The first shape was
a checkbox per catalogue row. The owner asked for what Qwen Code's provider wizard does instead — *"can we
facilitate the user simply entering the models preferred to use?"* — and the row became **typed entry**: chips
for what is offered, an add box taking one id or a pasted comma list with autocomplete against the fetched
catalogue, and browsing demoted to a collapsed click-to-add list for an id not memorised. The connect form
took a *model ids* field as well, so a key and its menu are one action (two calls: the runtime's `connect`
route accepts a credential only). The storage shape, the semantics and every acceptance criterion are
unchanged — this is the same `selected_models` value, edited by typing rather than by ticking.

**Why an unknown id is accepted and flagged rather than refused.** `set_selection` validates nothing,
`list_models` filters the fetched catalogue *to* the selection, and `provider_for` resolves only ids the
catalogue knows. So a stored id that the catalogue has never carried is invisible in the picker and refused
at send time by `"Selected model is not available for chat."` — a message naming neither the provider nor the
selection. Refusing it in the UI would be wrong too: the catalogue is fetched, and a model added upstream is
real before it is cached. The chip carries the caveat at the moment of typing, which is the only place that
can.

**A second finding, pre-existing and independent of gateways.** `handlers/conversation.py:60-67` deliberately
**ignores the model the client picked**: *"we deliberately do NOT honor ctx['model'] here — the frontend often
sends UI tier names like 'Home-AI-Swarm' that aren't real Ollama identifiers."* It resolves from the template
registry instead (`CONVERSATION`, default `qwen3:8b`). So today a plain chat turn on a **local** model is
answered by the registry's model, not the picked one, while a **gateway** turn is answered by the picked model
with no persona and no tools. Those two behaviours are individually defensible and jointly incoherent: the
picker means different things depending on which list the model came from.

The rule's premise does not reach a gateway id. `Home-AI-Swarm` is a UI tier name; `qwen/qwen3.8-flash` is a
real identifier the runtime resolved through `provider_for` and the gate admitted. Honouring the pick for
provider-backed ids is therefore not the bug that comment is guarding against, and the divergence should be
stated rather than left to rot.

**The enabling discovery.** `phi.model.openrouter.OpenRouter` exists in the installed phidata
(`mro: OpenRouter → OpenAILike → OpenAIChat → Model → BaseModel`) and carries `id`, `api_key`, `base_url`,
`tools`, `functions`, `run_tools`, `tool_choice`, `system_prompt`, `instructions`. So the agent layer does
**not** need a hand-rolled client or a fork of the tool loop: the `Agent` stays, only the model object
changes. Every current agent imports `phi.model.ollama.Ollama` and nothing else — this is the first crack in
an Ollama-only assumption, which is why D6 recorded "a provider-backed orchestrator needs its own design".

**Shape.** A factory, one place, returning the right phi model for a resolved id:

```
model_client(model_id, uid) ->
  provider_for(model_id) == "openrouter"  -> OpenRouter(id=model_id, api_key=get_key(uid,"openrouter").get_api_key())
  otherwise                               -> Ollama(id=model_id, host=get_best_host_for_model(...), options=...)
```

Key material comes from `provider_keys.get_key(uid, provider).get_api_key()` — the same Fernet-decrypted path
`list_models` already uses, never a new store. `get_best_host_for_model` and `get_ollama_options` must not be
called for a gateway id at all: they resolve an Ollama host from a model name and would return a host that
cannot serve it.

**Acceptance.**
(a) A turn on a selected gateway model arrives with the conversationalist's `instructions` and history, and
    says it is Memex. Proven by sending the owner's exact test prompt again and reading the answer.
(b) The same turn can call a tool the persona offers it, and the result streams back through the existing
    event contract — `tool_start` / `tool_result` already survive to the desktop on the local path.
(c) A local turn is unchanged: same model resolution, same host, same tools. Asserted, not assumed, because
    the factory now sits in front of both paths.
(d) The picker means the same thing on both paths. **Resolved by the owner on 2026-09-29: yes, honour the
    pick, and make it per-session** — so this criterion is discharged by D8 honouring `request.model` for a
    local conversational turn, and by **D9** below for the persistence semantics. No turn is served by a model
    other than the one named without saying so.
(e) No key material in a log, an event, or the transcript. The gateway client is constructed per turn from
    the encrypted store; nothing writes it to `config.json` or echoes it.
(f) A gateway model whose provider does not support tool calling degrades to a plain completion and **says
    so in the stream**, rather than failing silently mid-answer.

**Built 2026-09-29 — slice 1, the factory.** `agents/providers/model_client.py` answers "who can serve this

Two measurements changed its shape while it was being written:

* **The dispatch index is process-local.** In a cold process `providers.openrouter_catalogue.known_ids()`

## D9 — the model is chosen per session, seeded from the profile default (owner's rule 2026-09-29)

**Today:** `store.ts:65` holds one global `selectedModel`, persisted at `:359`, written by
`setSelectedModel` at `:327`. Sixty-seven references across the renderer, but only about ten real consumers
(`ModelPickerPopover`, `InputBar`, `SteeringCard`, `ScheduledTasks`, `ContextMeter`, `StatusBar`,
`SettingsView`, `EvalBenchView`) — and every one of them means *"the model for what I am looking at"*. That
coincidence is what makes this tractable rather than a sweep.

**Rule to implement.**
- A session carries its own model. Switching threads switches the model; a thread you set `qwen3:14b` on does
  not become `qwen/qwen3.8-flash` because a different thread was used last.
- A **new** session seeds from the active profile's default model — not from whatever the previous session
  happened to use.
- The picker writes the **session's** model. The profile default remains the seed and the thing Settings
  shows; a deliberate "make this my default" is the only action that changes it.

**Why the shape matters more than the plumbing.** `applyProfile` in the picker currently recomputes
`selectedModel` from `routing.default` / `profile.defaultModel` on every profile load and every profile
change, which is a *global* overwrite. With per-session models that same code would stomp each session back to
the profile default on the next launch, so the persistence rule and `applyProfile` have to be reconciled in
one change, not two. D7's `defaultModelSource` is the seed-side half of that.

**Acceptance.**
(a) Two sessions, two different models; switching between them changes the trigger, the status bar and what a
    turn sends — asserted, not assumed, because all three read the same field.
(b) A new session starts on the profile default, whatever the previously active session was using.
(c) The choice survives an app restart per session, and a profile switch does not rewrite sessions that
    already carry a model.
(d) Sessions that predate the change — persisted with no model of their own — resolve to the profile default
    rather than to a stale global. The store already has a versioned migrate at `:386`; this rides it.
(e) Scheduled tasks and the model arena, which read the global today, say which session's model they used
    instead of silently inheriting whichever thread happened to be focused.
(f) `ContextMeter`'s window follows the session's model, not a global one — otherwise the meter describes a
    model that is not answering.

**Order:** D8 first (the harness must honour what it is sent, or a per-session pick on a local model still
gets answered by `qwen3:8b`), then D9. D9 is app-only and needs no restart; D8 needs one.

**D8 accepted live 2026-09-29.** After `docker restart agent_runtime`, a streaming turn on
`qwen/qwen3.8-flash` as `Justin` came back with `chatcmpl-swarm` chunk ids — not `chatcmpl-openrouter` —
which is the proof the routing cut worked and the turn reached the router instead of the raw branch. The

CODE/DEVOPS/IMAGE/3D/RESEARCH — replacing the invented "no filesystem access, no code execution, no memory"

**Gate follow-up built 2026-09-29 - the cold index.** `_apply_model_policy` asked `provider_for` directly, and that index is only as good as the process's fetched-catalogue cache. Measured before and after in a genuinely cold container process for `qwen/qwen3.8-flash`:

| | |
|---|---|
| catalogue ids in a cold process | **4**, `fetched_at: None` |
| old gate `provider_for(requested)` | **None** -> 400 *"Selected model is not available for chat."* |
| new gate `provider_of(requested, uid)` as `Justin` | **openrouter**, from the stored selection |
| new gate as an unknown uid | **None** - the fallback cannot admit someone else's selection |

So the first gateway turn after a restart was refused until something unrelated warmed the cache. **The acceptance run earlier in this section did not catch it, because it was preceded by a `/v1/models` call - one of the things that refreshes the catalogue.** A check that warms the state it is meant to exercise proves nothing about the cold path; that is the confound worth keeping.

**D9 store slice built 2026-09-29 (`181652b`).** `Session.model` holds the choice, and `selectedModel` — the
one field ten consumers read, each meaning *"what answers the next turn here"* — is kept in step with the

nobody chose for inherits `profileDefaultModel`, held apart and **not** persisted: a seed that outlives a

and (f) are unit-only so far.
