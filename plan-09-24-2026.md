# Memex: Website ↔ Desktop Realignment

## Context

Tonight's debugging session (model-selection wiring for Collective runs) surfaced the
actual root cause behind repeated confusion: **two backend trees are being maintained
as if they were one product.** `Memex_Core` (Lovelace) is demonstrably ahead —
`role_model_resolver.py`'s single-model snapshot binding doesn't exist at all in
`Agent_Swarm` (Turing) — yet the public "Memex Anywhere" profile silently routes to
the older tree, so a real fix landed in one place and not the other.

Decision made: stop trying to keep the public website (`Memex_Core/ui`, deployed on
Turing behind `memex.shivelymedia.com`) at feature parity with the Desktop app. The
website becomes a **media/download/info site plus an admin/fleet-ops backend**; the
Desktop app becomes **the one place real development, routing, and swarm work
happens** — each install pointing at whatever inference engine(s) its own user
brings (their own Ollama, their own llama.cpp, their own rig), not a shared hosted
backend. Desktop also gains a **guided local-infra setup** so a brand-new user with
nothing installed can get running.

This plan covers three phases: (A) prune the website down to its new scope, (B)
confirm the desktop app needs no new dev/runtime features (it already has them —
this is a subtraction project on the website side, not new desktop work), and (C)
build the guided Ollama/llama.cpp install flow.

## Phase A — Website (`Memex_Core/ui`) split

`ui/` is a Next.js app (`ui/src/app/...`) with two coupled things: page routes and
server-side API proxy routes (`ui/src/app/api/**`) that the *outside world* uses to
reach the backend — including `api/backend/[...path]`, the exact catch-all proxy
`https://memex.shivelymedia.com/api/backend` resolves through, which is what the
Desktop app's **"Memex Anywhere" profile depends on**. Pruning has to distinguish
"duplicated product surface" (delete) from "infrastructure the Desktop app still
calls" (keep).

**Keep (admin/fleet-ops + infra):**
- Pages: `ops/`, `monitor/`, `monitoring/`, `governance/`, `mission-control/`, `docs/`
- API routes: `api/devops/**` (git, ssh, log streaming), `api/grafana/[...path]`,
  `api/langfuse/[...path]`, `api/maintenance/[...path]`, `api/services/health`,
  `api/auth/**` (Authentik session)
- **`api/backend/[...path]`** — do not remove; this is the tunnel proxy the Desktop
  app's remote profile uses. Removing it breaks "Memex Anywhere" entirely, which is
  a separate decision (see Open Question below), not a side effect of this cleanup.

**Remove (product surface, now desktop-only):**
- Pages: `swarm/`, `dev/`, `tools/`, `routines/`, `research/`, `art-studio/`,
  `training/`, `control/`, `palace/`, and their dedicated component trees under
  `ui/src/components/{swarm,dev,tools,routines,training,art-studio,palace,...}`
- Corresponding nav entries in `ui/src/components/layout` (or wherever the site nav
  is defined — confirm exact file during implementation)

**Add (new scope):**
- A landing/download page (link to the Desktop app installers once Phase C's
  multi-platform builds exist)
- Media/info content pages per your existing `docs/` pattern

## Phase B — Desktop app: no new runtime work needed

The Desktop app (`memex-desktop`) already has the dev/runtime surface this plan
consolidates onto: chat + Collective (`InputBar.tsx`, `sse-stream.ts`), Scheduled
Tasks, model picker (`ModelPickerPopover.tsx`), and multi-profile routing
(`electron/config-store.ts`). This phase is a **verification pass, not new
construction**: confirm nothing the website's removed pages did (e.g. `art-studio/`,
`training/`) has a gap on the desktop side before those website pages go away. Flag
any real gap found as its own follow-up rather than blocking the website prune on it.

## Phase C — Guided local-infra setup (Ollama / llama.cpp)

Extends existing, partially-built scaffolding — this is *not* greenfield:

- `src/components/onboarding/SetupWizard.tsx` already does hardware inspection
  (RAM, GPU + VRAM), model recommendations, and an Ollama reachability/pull flow.
- `electron/local-llm.ts` already has `inspectLocalLlm()` and
  `recommendLocalModels()`.
- What's missing: `openOllamaDownload()` today only opens a browser tab — there is
  no actual installer automation, no llama.cpp path at all, and electron-builder's
  `package.json` currently only configures a **Windows/nsis** target (no `mac` or
  `linux` block yet), so cross-platform distribution isn't wired up regardless of
  the installer work.

**C1 — Engine choice UI** (new wizard step, before the existing Ollama step):
Explain the real trade-off surfaced tonight — Ollama is the multi-model swap engine
(loads/evicts on demand, needed for Team Builder-style per-role model variety);
llama.cpp is a single pinned model with disk-persisted KV-cache (`/slots/save|restore`),
worth it for one long-context, latency-critical lane, at the cost of not swapping
models on demand. Let the user pick Ollama, llama.cpp, or both — no silent default.

**C2 — Per-OS installers**, new functions in `electron/local-llm.ts` alongside the
existing `inspectLocalLlm`:
- Ollama: `winget install Ollama.Ollama` (Windows) / `brew install ollama` or the
  official `.dmg` (macOS) / the official `curl -fsSL https://ollama.com/install.sh | sh`
  (Linux)
- llama.cpp: use prebuilt per-OS binary releases from the `ggml-org/llama.cpp`
  GitHub releases — **not** a Docker Desktop requirement, since a "brand new user"
  shouldn't need Docker as a prerequisite (this differs from how your own Lovelace
  rig runs it tonight; document that divergence in the wizard copy)
- Every install action is a real system change (installing software, possibly
  invoking `sudo`/UAC) — each one gets an explicit confirm step in the wizard before
  running, consistent with how this session has treated other system-modifying
  actions; no silent/background installs.

**C3 — electron-builder multi-platform packaging**: add `mac` (dmg) and `linux`
(AppImage/deb) target blocks to `package.json`'s `build` config, alongside the
existing `win`/`nsis` block. Prerequisite for C1/C2 to reach non-Windows users at
all — currently unbuilt for those platforms regardless of installer code.

## Open question — remote access to Lovelace

`api/backend/[...path]` is kept in Phase A specifically because "Memex Anywhere"
depends on it today, tunneling to **Turing's** `Agent_Swarm` backend — the tree that
still lacks the model-selection fix from earlier tonight. This plan does not decide
whether to (a) port that fix to `Agent_Swarm` so remote access stays fully
functional, or (b) leave remote access on `Agent_Swarm` as a known-degraded path and
treat "reach Lovelace from outside the LAN" as a separate, later problem. Flagging
so it isn't silently decided by omission — worth a explicit call before Phase A ships.

# Desktop-side realignment (added 2026-09-24, after the open question was answered)

Owner decisions recorded this session, verbatim intent:

1. **"There will be no more Memex Anywhere."** The hosted profile dies. The open question above is
   closed by deletion — `api/backend/[...path]` no longer needs keeping *for the desktop*; whether the
   site's own admin pages still call it is now a Phase A question only, and the Phase A verification
   step that curls that endpoint is no longer a desktop acceptance check.
2. **Desktop owns model routing; `config.json` is the source of truth** (the qwen-code / codex shape:
   a hand-editable file that assigns models to features). The runtime honours what the client declares
   instead of resolving roles against a shared host.
3. **Guided setup is keyed on run style.** The user picks how their box runs — one pinned model on one
   GPU, or multi-model across one-or-more GPUs — and the wizard installs and configures the engine
   (Ollama or llama.cpp) that matches, so the Memex features actually work in that mode.
4. **The desktop controls Team Builder's per-role map** (owner, 2026-09-24: "The desktop should be
   controlling the Team Builder's map, since this is a local harness"). Consequence, and it is the shape
   D1c takes: the runtime stops deciding roles from its own environment and accepts a client-supplied map,
   which means a new request field, a third snapshot `source`, and honouring it on restore instead of
   coercing it back to `team_builder` (`role_model_resolver.py:175` collapses anything unknown).
   **Name the keys against the runtime's actual roles, not the desktop's current slots.**
   `_SWARM_ROLES` is `coordinator, architect, coder, devops, researcher, analyst, verifier` — seven. D2's
   slots are `default, code, collective.coordinator, collective.critic, embedding` — five, and two of them
   (`critic`, `embedding`) are not swarm roles at all while four roles have no slot. A map keyed by the
   slot names would be accepted by a permissive server and bound to nothing, which is the silent no-op this
   project keeps recording. Decide explicitly, in D1c: which slots project onto which roles, and what the
   app does with a role it has no slot for.

5. **Setup is scenario-driven; "where the orchestrator lives" is an output, not a choice.** Owner,
   2026-09-24: multi-model on one GPU → the orchestrator runs on this machine beside that card; multi-model
   on multiple GPUs → same, but with a per-GPU assignment layout; LAN / homelab → the user organises the
   orchestrator placement **and the agent roster** around the topology the wizard identified. In their
   words: *"It's not so important of 'where', but that the proper assignments/setup is performed with
   whatever that scenario is."* Consequences:

   - The wizard's product is a **topology + assignment set**, not a model dropdown. Shape: scenario →
     engines and lanes → which GPU each lane may use → which model each role gets → confirm → write. This
     re-scopes D3a-2's "slot editor" into **role assignment against the runtime's seven roles**, which is
     what decision 4 already implies.
   - `config.json` needs a lane→GPU field it does not have. `engines.<id>` today carries only
     `kind`/`baseUrl`/`label`/`pinnedModel`; nothing expresses "this llama.cpp lane lives on card 1", which
     the multi-GPU scenario requires and `gpu_queue` already enforces server-side.
   - **Scheduled routines run only while the app is open — for the local scenarios.** The owner chose that
     explicitly, so no background daemon is needed locally and a supervised in-app process suffices. But the
     statement is placement-dependent, not universal: on a LAN/homelab orchestrator the runtime is a service
     on another machine, and its `trigger_scheduler.py` fires whether or not this desktop is running. The
     Routines screen must therefore say the rule **per placement** — a blanket "only while Memex is open"
     would be a new lie on a homelab install, which is the failure class this plan keeps naming.
   - **D1c survives every branch of this decision.** Whether the orchestrator is app-supervised locally or
     organised by the user on the homelab, the desktop still has to *send* the role map and the runtime still
     has to *honour* it. What changes is the deployment hazard: if the app ships and supervises the runtime,
     the two halves of the contract ship together and can never be half-applied — which is precisely the
     risk that made me insist on runtime-first for a separately-deployed server.

`src/lib/memex-client.ts:39-64` (`listModels`, `fetchOllamaModels`) hits
`{agentRuntime}/v1/models/ollama`, and `electron/health.ts:41-47` derives inference health from the

The desktop already has the other half: `electron/local-llm.ts:73-89` reads `http://[::1]:11434/api/tags`
directly, and `electron/ollama-residency.ts` (from `7235f11`) counts residency by load identity.

- **Two caveats D1a/D1b do not clear, recorded rather than glossed:**
  1. For `providerType: "internal"` profiles — both seeds — *whether the picker opens at all* is still

     Failing open on permissions is a security-posture change, not a plumbing fix, and belongs with D2.
  2. Nothing writes `llamaCpp` yet: `RuntimeProfile.llamaCpp?` exists and the registry honours it, but the

## D2 — The routing table — **landed `9f9bfa7`**

`electron/routing-config.ts` (pure) + `runStyle` / `engines` / `routing` as three top-level keys in
`config.json`, derived on first load from the profile's existing `ollama` + `defaultModel`. Verified at
that commit: typecheck clean, **42 files / 245 tests**, `npm run build:renderer` succeeds.

**First piece of real acceptance since `0.1.109`:** the app was run from a dev build at `83ec632` on the
owner's install (home-lan profile, live Ollama at `192.168.2.101:11434`), a model was picked from the
picker, the app was quit from the tray and relaunched, and **the selection was still the picked model** —
which is the exact behaviour the `9f9bfa7` write-back exists to provide, and the first time it has been
observed outside a test. Reported by the owner, not observed by me: I cannot see the window, so the chip's
rendering, the engine chips and the `routed from routing.default` label remain unverified in a running app.
No packaged installer has been produced since `14b0d6c`, so this was a `vite build` + `electron .` run
against `%APPDATA%` config, not a qualified release.

Three things worth knowing before D3 builds on it:

- **A pick writes the table.** `routing.default` in both styles; in `single` it also moves that engine's
  `pinnedModel`, because `flattenForRunStyle` resolves every slot onto the pin and would otherwise
  override the choice under a different name. The first
  version of this slice wrote only `profile.defaultModel`, which the load path then lost to the table —
  a selection reverted on next launch, i.e. the silent substitution the module exists to prevent. Four
  tests now pin it, including the round trip (`resolveRoute(written, "default")` returns the newly picked
  model) and a visible refusal. All four fail without the write-back; confirmed by neutering it.
- **`saveRouting` refuses rather than repairs**, and every issue carries a path
  (`routing.collective.critic.engine: names no engine…`) — the hand-editable premise depends on that, and
  an unreadable `config.json` is never written over this session.
- **Still open, by design:** `flattenForRunStyle`, `pinnedTarget`, `routing:set` and `routing:validate`
  have no production caller beyond the picker's default slot; `saveRouting` broadcasts no
  `config:changed`, so a hand-edit is read at next load rather than live; `runStyle` is never *derived* as
  `single` (choosing a style is D3's job); the per-slot application to real requests is still D1c; and
  nothing here has been run in a packaged app or inspected natively.

## D2 — original brief

`config.json` gains an `engines` map, a `runStyle`, and named slots. Slot names come from what the app
already routes over (chat, code, collective coordinator/critic, research, embed, image) — not from the
runtime's internal role strings.

```jsonc
{
  "runStyle": "multi",                       // "single" = pinned model, "multi" = swap on demand
  "engines": {
    "ollama-local": { "kind": "ollama",    "baseUrl": "http://[::1]:11434" },
    "llama-local":  { "kind": "llama.cpp", "baseUrl": "http://127.0.0.1:8080", "pinnedModel": "…" }
  },
  "routing": {
    "default":                { "engine": "ollama-local", "model": "qwen3:14b" },
    "code":                   { "engine": "ollama-local", "model": "qwen3.8:27b" },
    "collective.coordinator": { "engine": "ollama-local", "model": "qwen3.8:27b" },
    "collective.critic":      { "engine": "ollama-local", "model": "qwen3:14b" },
    "embedding":              { "engine": "ollama-local", "model": "nomic-embed-text:latest" }
  }
}
```

Two hard constraints, both verified in code:

- **The `model: "swarm"` sentinel is load-bearing.** `src/lib/sse-stream.ts:146,170` defaults `model` to
  `"swarm"`, and the runtime's `_routes_to_dev_harness()` exempts model `swarm` when deciding whether a
  `dev_mode` request is a coordinator turn (`Memex_Core/agents/main.py`, same shape in `Agent_Swarm`).
  If the desktop starts putting real routing data in `model`, the sentinel must move to its own field on
  both sides in the same change — a desktop-only edit silently reroutes coordinator turns. Not a
  desktop-side task: needs a runtime commit in the tree that actually serves (`Memex_Core`).
- **`runStyle: "single"` cannot honour a per-role table.** llama.cpp pins one model, so per-slot variety
  is physically unavailable. The desktop must validate its own table against `runStyle` and flatten
  deliberately — tell the user every slot resolves to the pinned model — rather than sending a table the
  engine can't satisfy. This mirrors `SNAPSHOT_SOURCE_SINGLE` in `role_model_resolver.py:78` and
  `:257-261`, so the two sides already have a shared vocabulary for it.

## D3 — Run-style guided setup (replaces the removed choice card)

`SetupWizard.tsx` loses the Memex Anywhere card and gains, in its place: hardware read → run style →
engine install → routing table seed. `electron/local-llm.ts:23-45 recommendLocalModels()` already
tiers by VRAM and `:73-89` already probes Ollama + the harness, so the reading half exists; what's
missing is the *install* half (Phase C2) and the style gate.

- **The AdapterRAM defect — fixed in `0dbdec0`, which is what unblocked the run-style step.**
  `detectGpus()` read `Win32_VideoController.AdapterRAM`, a UInt32 saturating at 4,294,967,295 bytes, so
  any card of 4 GB or more read as 4.0 GB and a 24 GB box fell into the entry-level tier; it also returned
  `[]` on every non-Windows platform. `electron/local-llm.ts` now probes per platform — `nvidia-smi` first
  on Windows and Linux, `system_profiler` on macOS, WMI only as fallback — and a saturated or negative
  `AdapterRAM` yields `vramGb: 0`, which the wizard renders as "memory unknown" instead of inventing a
  number. Evidence on this host: `nvidia-smi --query-gpu=name,memory.total --format=csv,noheader,nounits`
  returned two `NVIDIA GeForce RTX 5060 Ti, 16311` rows → 15.9 GB each → total 31.8 GB → the 24 GB+ tier.
  **Unverified, stated as such:** the macOS and Linux probes have never run on their platforms (this is a
  Windows host), and the WMI fallback is exercised only by unit fixtures — on this machine the primary
  probe answers, so the fallback path is not reached in practice here.
- `recommendLocalModels()` hardcodes four model ids (`qwen3.8:27b`, `qwen3:14b`, `qwen3:8b`,
  `gemma4:e4b`). D2's config file replaces that with user-editable defaults per tier, otherwise the
  wizard keeps shipping a curated list nobody can change without a rebuild.
- **The harness gap — decided 2026-09-24, one sub-question still open.** The owner's rule: *the harness
  supports whatever Ollama or llama.cpp the user already has (scan for it, or ask for the install
  location), or the desktop app installs either one on the user's behalf, chosen from their hardware and
  usage approach, and then sets up the runtime — staying as model-compatible with the feature set as
  possible.* Four requirements fall out of that sentence, and each is a distinct piece of work:

  1. **Discover an existing engine.** Today `inspectLocalLlm()` probes one hardcoded address
     (`LOCAL_SERVICE_DEFAULTS.ollama = http://[::1]:11434`, `electron/local-llm.ts:21`) and reports
     reachable/not. It never looks for an installed binary that isn't running, never checks a custom
     port or `OLLAMA_HOST`, and has no llama.cpp path at all. "Scan / ask for install location" is new.
  2. **Install an engine on the user's behalf.** Phase C2 as written (winget / brew / official script,
     each behind an explicit confirm).
  3. **Select the engine from hardware + usage style.** The run-style step above, which is why the
     `AdapterRAM` defect blocks D3: the selection input is currently wrong on 24 GB+ cards.
  4. **Configure the runtime from that result**, replacing the wizard's present contract. What exists
     today is `ipc-handlers.ts:741-756`: the renderer posts back `{ harnessUrl, mempalaceUrl, ollamaUrl,
     openWebUiUrl, comfyUiUrl, model }` and a profile is written from it — i.e. **the user is asked to
     type URLs**. "Engage the app to install and set up" means that payload becomes a derived artefact,
     not a user input.

  **What their answer does not settle, kept visible rather than decided by omission:** with the engine
  installed and configured, a request still has to reach an agent runtime, and every feature in this app
  calls `getAgentRuntime()`. Grepping `electron/` for process supervision returns only terminal PTYs
  (`ipc-handlers.ts:343`), LSP servers (`lsp-manager.ts:102`) and the OpenSCAD runner
  (`openscad-runner.ts:89`) — nothing starts, stops or monitors a runtime process, and no code in this
  repo references `uvicorn`, Docker or a Python interpreter to launch one. So D3 still needs an owner
  decision on **who runs that process on a laptop with no LAN host**, with the same constraints as the
  engine (guided, no Docker prerequisite, works for a brand-new user). Absent a different call, the work
  proceeds on the default that fits those constraints — the app installs and supervises a local runtime
  (start/stop/crash-restart, port allocation, log capture, an uninstall path) — and D1/D2 are deliberately
  independent of which way that goes: they change *where models come from* and *what the request carries*,
  not *who hosts the orchestrator*. The comments that assert the old model — `electron/health.ts:31-32,44`
  and `electron/config-store.ts:112-114` ("The harness owns model routing", "the harness owns the
  Docker-internal Ollama route") — become false when D1 lands and must be rewritten in that change, not
  left as stale narration.

pin picker plus one line saying per-feature assignment is unavailable. Candidates come from the registry
catalogue rather than free text; a slot naming an unreported model warns and still saves; hand-written
slots outside the five survive; the in-session view is built from the write's response, since
`saveRouting` broadcasts no `config:changed`.

**Flaw — fixed in `f3ced0a`.** `proposeRunStyle`'s first rule proposed `multi` when VRAM cannot be
measured, while its own explanation said nothing was being claimed — that *is* a claim, and a wrong-shaped
one: a CPU-only 32 GB laptop and a 24 GB AMD card whose `AdapterRAM` saturated at the UInt32 ceiling both
landed there and want opposite styles. `RunStyleProposal.runStyle` is now `RunStyle | null`, the wizard
labels the decline ("not proposed — this probe cannot tell"), and still requires a click. `systemRamGb`
appeared in every `why` string and conditioned no rule; it left the signature, and the wizard shows RAM as
a fact about the machine rather than as evidence it never used.

One resolved design constraint to carry into that slice rather than rediscover: `ipc-handlers.ts:580-595`

## D4 — Model/feature compatibility matrix

"Staying as model compatible as we can with the feature set" is only enforceable as a table. Each Memex
feature names the capability it needs; the app checks the selected model against it and says so up
front. This is the direct answer to the failure class this project has been bitten by repeatedly — the
Gauntlet quality bar parsed and discarded, `research_mode` never reaching the coordinator, a completion
record implying a critic loop that never ran. Silent degradation is the bug; the matrix is the guard.

| Feature | Capability the model must have | If it doesn't |
| --- | --- | --- |
| Chat | instruction following, streaming | — baseline, everything supports it |
| Code / DevHarness | reliable tool + function calling (read/write/edit/exec round-trips) | disable the workspace, state why, point at a capable model |
| Collective coordinator | tool calling **and** long context (the perspective matrix plus its transcripts) | warn before the run; short-context models truncate silently |
| Collective critic / Gauntlet verdict | strict structured output — the verdict grammar (`VERDICT: PASS`) is parse-critical | refuse Gauntlet rather than run a critic that can emit unparsable verdicts |
| Research / Perspectives | several concurrent lanes, or one lane re-used serially | run-style dependent; single style collapses to serial |
| Memory (MemPalace) | a reachable **embedding** model — a separate slot from the chat model, `nomic-embed-text` today | memory writes queue instead of failing the turn |
| Image grounding / Design | vision input | hide the attach control for that model, don't 400 at send time |
| CAD / OpenSCAD, Unreal lanes | tool execution + long context | existing feature gates; the matrix should be the single source, not per-feature `if`s |

Acceptance for D4, per row: pick a model that lacks the capability, and the app must state the limitation
before the request rather than produce a transcript that implies capability it did not use. Where the
model registry can answer the question (`/api/show` capabilities on Ollama, `/props` on llama.cpp) the
matrix is derived; where it can't, the capability is a user-editable field in the routing entry — never a
guess baked into `src/`.
